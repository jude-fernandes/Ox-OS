# lockd throttling — lockouts that stop attackers, never owners

Date: 2026-09-07
Status: **DONE — PIN GATE ALL GREEN (extended with throttle drill)**

## Scope

Phase 3 chunk 19: the standard lockscreen defense, built on lockd.

- **Exponential backoff** — consecutive wrong PIN attempts arm
  increasing delays: 1s, 2s, 4s … capped at 60s. State lives in lockd
  (the secret's owner); a successful verify resets it instantly — the
  OWNER is never locked out of their own device.
- **Honest throttled verdicts** — a verify arriving inside the window
  is not evaluated at all: lockd answers
  `{ok:false, throttled:true, retry_after_ms}` and journals
  `pin-verify-throttled remaining_ms=…`. Wrong-PIN rejections journal
  `pin-verify-denied throttle-next-ms=…`.
- **Shell surfacing** — ox-shell distinguishes the verdicts: a
  throttled attempt shows the error strip and journals
  `shell-pin-throttled` WITHOUT counting a rejection (the attempt was
  never evaluated), and — critically — **clears the typed-digit
  buffer**.

## Gate

`tools/pin-gate.sh` (final form, all on one boot): rotation legs
(wrong-current refused → 1234→5678 self-verified) → relock from the
UI → old PIN rejected → new PIN unlocks → **throttle drill**: five
wrong PINs escalate the backoff to a 16 s window → the sixth full pad
injection lands inside it and surfaces `shell-pin-throttled` → the
owner waits out the window → unlock with the rotated PIN →
`pin-verify-success-after-failures` (reset journal) → denial journal
verified. Artifact: `2026-09-06-lockd.png` chain.

## Debug journey — three finds, two of them real bugs

1. **Gate choreography**: the drill's taps must happen on a LOCKED
   screen; the first version ran them after leg 9 had already
   unlocked (the shell ignores pad taps on the home screen).
2. **Throttle windows vs retry cadence**: two wrong PINs arm only a
   2 s window — the gate's next full pad injection (~9 s) always
   overshot it. The drill arms FIVE failures (16 s window) so the
   sixth injection demonstrably lands inside the throttle.
3. **A real shell bug: the throttled path never cleared the typed
   digit buffer**, so the user's next PIN entry was silently
   prefixed by the previous attempt's leftover digits
   (verify("66665678") → denied). Found because the gate's owner
   unlock failed with the CORRECT PIN. Fixed with `entered.clear()`
   on the throttled path.
4. Tooling note: two gate iterations were lost to my own edit
   scripts — one assertion-anchor mismatch that failed silently
   (traceback buried in output), and one grep pattern that didn't
   match the journal format. Both lessons: check edit-script output
   before trusting it, and keep milestone formats uniform.

## Honest limits

- Throttle state is in-RAM: a lockd restart clears it (acceptable —
  the secret itself is bcrypt-strength against offline attacks via
  the stretched hash; reboot-repersistent throttling is a Phase-5
  hardening item).
- No duress PIN / panic wipe yet (Phase-5; lockd's enroll op is the
  foundation).
- The shell's error strip says "wrong PIN / wait — try again" for
  both cases; a distinct countdown display is UX polish.

## Verdict

**PIN GATE ALL GREEN** (2026-09-07): throttle engages after
consecutive failures, is surfaced honestly by the shell, never locks
out the owner, and — the real find — the drill exposed and fixed a
digit-buffer corruption bug on the throttled path.

## Addendum — duress PIN (same chunk, one boot)

The lock story gained its covert layer: **lockd enrolls a duress PIN**
(`enroll-duress` op: current-PIN-gated, must differ from the real PIN,
atomic salted store at `lock.duress.pin`, self-verified; DEV default
9999 hashed at first boot for gate exercisability). A matching duress
PIN **unlocks the device but is flagged** — lockd journals
`pin-verify-duress`, the shell surfaces `shell-duress-unlocked` as the
hook point for panic-wipe/alert actions (Phase 5).

The first implementation had the composition backwards — duress was
AND-ed with the real-PIN verify, which can never both hold (they must
differ). The gate caught it because its owner-unlock leg failed with
the CORRECT PIN; the `duress-check` diagnostic line pinpointed it
(matched=true, ok=false). Fixed: matched duress unlocks flagged;
unmatched falls through to the real-PIN check. The earlier
digit-buffer lesson applied here too — the throttled path now clears
typed digits.

Gate legs (one boot, extended): rotation (self-verified) → relock from
the UI → old PIN rejected → real PIN unlocks → throttle drill (five
wrong PINs arm a 16 s window, sixth injection surfaced as throttled,
owner unlocks after the window) → **panic wipe**: relock → duress PIN
unlocks flagged → shell triggers lockd's `panic-wipe` → every user
secret under /data/ox destroyed (lock PIN, duress store, permission
grants, installed packages, contacts), journaled on both sides
(`shell-panic-wipe-triggered` + `panic-wipe-executed files=…`). The
duress flag now has real teeth: an attacker who forces the duress PIN
gets a device with no secrets left. Verdict: **ALL GREEN**.

Tooling note: the workspace-test gate blocked the first payload build
on a compile error in the new wipe code (a stray `?` in a
non-Result function) — the wiring paying for itself before any VM
time was spent.
