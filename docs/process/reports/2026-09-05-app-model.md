# App model — intentd + the first real apps (Settings gated end to end)

Date: 2026-09-05
Status: **DONE — APP GATE ALL GREEN** (launch → interact → close → reap
verified end to end; verdict at bottom)

## Scope

Phase 3 chunk 6: tile taps stop being a milestone log and become real
app launches. Before this chunk, "launch" meant the shell printed a
kmsg line and redrew a banner. Now:

### 1. `ox-intentd` — the app lifecycle daemon

- Supervised s6 longrun serving `$OX_SOCK_DIR/intentd.sock`.
- Ops: `start {app}`, `list`, `status`. The app name → binary map
  (`Settings → ox-settings`, `Files → ox-files`, `Terminal → ox-term`)
  **is** the packaged app set; anything else is refused by name and
  journaled (`intent-refused app=X reason=app-not-packaged`) — no
  silent failures.
- Spawns the app binary, tracks children, and reaps exits in a
  reaper thread (`intent-exit app=… code=…`). Idempotent start while
  an instance is already running.

### 2. `ox-shell` — launches become intents

The tile-tap handler sends `start {app}` to intentd. If intentd is
down the shell degrades to the banner-only launch — recorded, never
fatal. The shell never spawns apps directly.

### 3. `ox-settings` / `ox-files` / `ox-term` — first packaged apps

- **Settings** (gated): info cards, a live airplane-mode toggle,
  Close. Window at (190,80) 900×680 — oxcom stacks windows in
  creation order, so it renders over the shell and both are visible
  in the launch screendump.
- **Files** (packaged, gate next): directory cards sandboxed to
  `/data/ox` with `..` traversal refused, read-only file viewer,
  Up/Back/Close.
- **Terminal** (packaged, gate next): the first keyboard-driven app —
  printable keys accumulate via `key-recv`, Enter runs the line
  through `/bin/sh -c`, output captured and capped. V1 honestly
  limited to non-interactive commands, no `cd` state.

All three hold the contract: **a foreground app holds a powerd wake
lock from first draw to exit** (released on Close) — see finding 1.

## Gate

`tools/app-gate.sh`: boot locked → PIN unlock → Settings tile tap →
require the full chain `shell-intent ok=true` → `intent-start` →
`settings-ready` → tap the app's airplane toggle (screen 967,642) →
`settings-toggle state=on` → screendump → tap Close (967,712) →
`settings-close` → require intentd to journal `intent-exit`.
Artifact: `2026-09-05-app-model.png` (Settings on top of the shell,
toggle on).

## Debug journey — two real integration bugs

This chunk is the first time two GUI clients lived at once, and the
gate caught exactly the class of bug that only shows up then.

1. **Foreground apps vs idle-doze.** First run: launch chain green,
   toggle taps lost. Live-VM forensics (QMP screendump showed
   *"Display output is not active"*; kmsg showed
   `pm-autosuspend idle_s=401 locks=0`) proved the device had dozed:
   the shell releases its wake lock at unlock, nothing holds one
   afterwards, and taps injected during suspend windows simply
   vanish. A rapid probe volley caught an awake window and fired the
   toggle instantly — the app was never broken. Fix: foreground apps
   hold wake locks (product semantics — "user is in an app, screen
   stays on"), not a gate hack.
2. **Compositor IPC starvation.** Second run: no doze at all, launch
   chain fired instantly — yet the app never drew, and run 1's
   `window-new` had only been served at the exact moment the shell's
   tap clicks resumed. Root cause: oxcom's IPC closure held the
   **compositor lock for the entire request** — including
   `key-recv`/`click-recv`, which intentionally block up to 10
   minutes. One app's blocking input wait queued every other client's
   requests (rendering included) behind it. Fix: `handle_input_wait`
   routes key/click waits lock-free (they only pop per-window
   queues); all other ops keep the existing serialization. Added a
   two-client starvation regression test (client A blocks in
   `click-recv`; client B must be served within 5 s — the old code
   fails at 10 s). Also repaired stale test call sites in oxcom that
   had silently rotted when the click hub was added (only host-side
   `cargo test` compiles them; the Nix build does not).
3. Environment hazard: a failed run's QEMU survived as a zombie until
   its 15-minute watchdog expired, so the next run's QEMU died
   instantly on "Address already in use" for the VNC port. The gate
   now pkills stale QEMUs before booting.

## Honest limits

- App windows are not closed on process exit: a crashed app would
  leave a ghost window. Lifecycle teardown (intentd → oxcom
  `window-close`, or oxcom reaping dead clients) is the next
  lifecycle chunk.
- The app set is a compiled map in intentd. `.oxp` packaging + oxpkg
  (install, manifest, permissions) is the next chunk and will own the
  dynamic app set.
- Terminal cannot run interactive programs and does not track `cd`.
- Wake locks of crashed apps would leak (powerd does not yet reap
  locks from dead PIDs).

## Verdict

**APP GATE ALL GREEN** (2026-09-05): `shell-intent app=Settings
ok=true` → `intent-start app=Settings pid=…` → `settings-ready` →
`settings-toggle state=on` → screendump → `settings-close` →
`intent-exit app=Settings`. Every leg on its first attempt; the
launch chain completed 138 s into boot (the starvation fix also made
the whole session faster).
