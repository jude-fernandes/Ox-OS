# ox-shell — the home screen as a real app (tappable launch tiles) +
# lock screen

Date: 2026-09-05
Status: **DONE — SHELL GATE ALL GREEN** (lock → unlock → launch
verified end to end; verdict at bottom)

## Scope

Phase 3 chunk 2+4: the home screen stops being a picture and becomes
an app, and the device boots into a lock screen. Two parts:

### 1. Compositor protocol: click delivery (`oxcom`)

- New `ClickHub` in `pointer.rs` — the pointer-side twin of
  `keys::KeyHub`: per-window click queues (bounded), condvar-blocked
  `pop(timeout)`.
- On pointer Down, after hit-testing the window under the cursor,
  oxcom pushes a **window-relative `ClickEv {x, y}`** to that
  window's queue — *before* focus/raise handling, so apps see every
  click on them, raised or not.
- New IPC op `click-recv {window, timeout_ms}` (mirrors `key-recv`);
  `window-close` drops the window's click queue.

### 2. ox-shell (`rust/crates/ox-shell`)

- Owns a window (1000×700 at origin), and **boots locked**: a lock
  screen with the wall clock (UTC HH:MM, no date-library dependency)
  and a tap-to-unlock button. Unlocking reveals the launch grid
  (Settings / Files / Terminal / Payments) drawn via ox-ui; the home
  screen is pre-rendered behind the lock so unlock is instant.
- Unlock/hit-test flow: blocking `click-recv` loop; the unlock button
  and each tile are hit-tested against their own rects; launches
  escalate (kmsg `shell-launch app=<name>`) and redraw with a launch
  banner. Unit tests: grid geometry, tile hit-testing, unlock-rect
  bounds and touch-target size.
- **Wake lock until first unlock** (`shell-screen`): a phone is awake
  while the lock screen shows, and the gate's scripted unlock must
  not be frozen by the idle doze (learned the hard way — see below).

## Gate

`tools/shell-gate.sh`: boots with the display; requires
`shell-locked` + `shell-home`; then injects **real pointer taps**
through QMP `input-send-event` with per-step retry (tap → poll the
milestone → retry up to 3×): unlock button (500,458) must produce
`shell-unlocked`, then the Settings tile (158,195) must produce
`shell-launch app=Settings`; saves a screendump artifact.

## Debug journey

1. First run: injection accepted by QMP but the guest saw nothing —
   no moves, no raise. Root cause never isolated (that boot was on a
   recycled, slow VM); the retry choreography made the gate robust to
   it, and the subsequent run delivered everything on the first
   attempt.
2. `handler_clicks` was accidentally cloned after the `serve` call
   and the handler function needed the hub as a parameter — caught by
   rustc (E0425), fixed along with the test call sites.
3. Recurring environment hazard: the WSL VM recycles between turns
   and wipes /tmp — gate runners must be self-contained (build +
   clone + run in one command).
4. The unlock tap was eaten by the idle-doze suspend at exactly the
   wrong moment (moves arrived, no click processing). Fix: shell
   holds the `shell-screen` wake lock until first unlock + per-step
   retry in the gate. Second run: unlock needed the retry, launch
   landed immediately — the design absorbed both failure modes.
5. rustc: `?` on the button layout error inside an io::Result
   function (String doesn't convert to io::Error) — handled
   explicitly with a journal entry.

## Honest limits

- "Launch" currently means: milestone + visual launch-banner state.
  Real app lifecycle (spawn the app's window/process) lands with the
  app model (`.oxp` + oxpkg chunk).
- The lock screen is a UI + state-flow gate: it proves the lock →
  unlock plumbing. Real authentication (PIN via key-recv, biometric,
  duress PIN) is the next security chunk and builds directly on this
  state machine.
- No hover/long-press semantics yet.

## Addendum — PIN authentication chunk (same day)

- The lock screen's tap-to-unlock became a real PIN state machine:
  12-key pad (1-9 / C / 0 / OK) laid out 3×4 from `PAD_ORIGIN (353,420)`,
  90×56 cells (ox-ui enforces the 48 dp touch target at build time),
  one `*` marker per entered digit (capped at 8), a danger error strip,
  and **clear-on-reject** — without it, stale digits poison the next
  attempt.
- PIN store: `/data/ox/lock.pin`, written on first boot with the
  **DEV ONLY plaintext default 1234**. Production is a hashed verifier
  + secure enrollment — a tracked chunk; this never ships as-is.
- Gate rewritten: `inject_pin` taps the digit centers **and then OK** —
  the first version tapped only digits, so the PIN was never evaluated
  (diagnosed by the wrong-PIN leg "passing" trivially while the unlock
  leg failed). Added a drill-settle wait (poll `resourced-tier-ok`)
  before PIN injection so the resourced memory drill can't thrash taps
  away, a wrong-PIN leg (9999 → `shell-pin-rejected`, device still
  locked, detected by count increase across retries), the correct-PIN
  leg (1234 → `shell-unlocked`), then the Settings-tap launch leg.
- Verdict: **SHELL GATE ALL GREEN** — reject wrong PIN, unlock on the
  correct PIN, tap-to-launch, end to end with screendump.
