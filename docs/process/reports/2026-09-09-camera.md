# Camera bring-up — chunk 35, Phase 4, 2026-09-09

## Claim

Ox OS runs the REAL V4L2 capture stack end to end on the virtual
target: kernel videodev + vivid (the kernel's virtual test sensor)
at /dev/video0, owned through the standard capture path — QUERYCAP,
G_FMT/S_FMT (BGR24, 320x240), read() — by ox-camerad, which serves
captures through the SAME honest-permission contract as locationd:
deny refused, fake clearly-synthetic, grant a REAL frame from the
sensor saved to /data/ox/DCIM and pinned by colorbar analysis
(vivid's 8-bar strip: colors=8). Nothing is mocked above the sensor;
on devices the identical daemon talks to real MIPI/USB sensors
through the same ioctls.

## Stack layers (all gated)

1. **Kernel** (fragment in `kernel/kernel.nix`): MEDIA_SUPPORT,
   VIDEO_DEV, the test-driver menu gates (MEDIA_TEST_SUPPORT,
   V4L_TEST_DRIVERS) and VIDEO_VIVID + VIDEOBUF2_* + VIDEO_V4L2_TPG
   as modules. The module set ships xz-decompressed
   (`camera-modules` derivation) and the selftest insmods them in
   the exact order vivid's modules.dep declares (mc, videobuf2-*,
   videobuf2-v4l2, videodev, v4l2-dv-timings, cec, v4l2-tpg, vivid).
2. **Driver** (`ox-camerad`, std+libc Rust, 6 unit tests in every
   payload build): owns the capture path via the V4L2 read() I/O
   method — QUERYCAP (verify CAPTURE|READWRITE), G_FMT, S_FMT,
   read() — converts BGR→RGB, writes PPM atomically to
   /data/ox/DCIM, and analyzes the frame (distinct bar colors) for
   the gate's ground truth. Policy layer mirrors locationd exactly:
   permstored `camera.read` consulted per capture — deny refused,
   fake serves a deterministic synthetic frame (never the sensor's),
   grant serves the sensor. Receiver-less boots stay up (no-flap).
3. **Selftest** (s6 longrun `camera-selftest`): wake lock, insmods,
   waits for /dev/video0, then walks deny → fake → grant for app
   camera.test, journals per-leg milestones, restores deny.
4. **Verification** (`tools/camera-gate.sh` ALL GREEN):
   `camerad-ready` → `camera-vivid-ok device=/dev/video0` →
   `camera-deny-refused` → `camera-fake-synthetic` →
   `camera-capture path=/data/ox/DCIM/IMG_0002.ppm colors=8 w=320
   h=240` (synthetic:false) → `camera-test-ok`.

## Instructive findings (the cost of doing this honestly)

1. **Kernel kconfig renames are silently fatal under
   ignoreConfigErrors.** VIVID does not exist in 6.18 — the media
   kconfig rework renamed it VIDEO_VIVID. The stale name produced NO
   error and NO module; the diagnosis came from diffing the final
   .config against the fragment. Same class one level up: the whole
   test-drivers menu (V4L_TEST_DRIVERS) defaults to N, and without
   it VIDEO_VIVID is unreachable and dropped. Two kernel rebuilds
   were consumed by this; the fix is to grep the built config, not
   trust the fragment.
2. **Module dependencies must come from modules.dep, not intuition.**
   vivid's load failed on `Unknown symbol vb2_ioctl_qbuf` et al until
   the module set matched vivid's modules.dep line exactly: 11
   modules including three non-obvious ones (videobuf2-v4l2,
   v4l2-dv-timings, cec). insmod order now mirrors that line.
3. **The often-quoted V4L2 ioctl numbers are the 32-bit-compat
   encoding.** On 64-bit, struct v4l2_format is 208 bytes (the
   embedded v4l2_window carries pointers → 8-byte alignment), so
   VIDIOC_G_FMT=0xc0d05604 and VIDIOC_S_FMT=0xc0d05605 — not
   0xc0cc5604/05. The wrong number returns ENOTTY ("Not a tty"),
   which cost one cycle to localize; the fix was compiling a
   5-line probe against the host kernel headers and treating THAT
   as the pin. Unit tests now assert the verified numbers and the
   pix-member offset (8), and the header comment warns future
   readers.
4. **musl vs glibc prototype drift**: musl's ioctl takes the request
   as c_int, glibc as c_ulong. The host test build compiled fine and
   the guest build did not — resolved with an explicit
   target_env-split cast that preserves the 32-bit pattern.
5. **vivid draws its moving cross through the exact middle row**
   (full-width arm), so a middle-row colorbar sample counts the
   cross (2 colors), not the bars. The analysis now samples rows at
   h/6 and 5h/6. The gate caught this as colors=2 on an otherwise
   successful real capture.
6. V4L2_CAP_READWRITE is 0x01000000; an initial wrong constant made
   the caps check pass spuriously — harmless here only because the
   read() path would have failed honestly anyway; fixed and pinned.

## Honest scope

- The Camera app (viewfinder, shutter UI, compositor in-use
  indicator) is the NEXT chunk; this chunk gates the HAL + service +
  permission layer. The hardware privacy shutter is hardware-scope;
  the in-use indicator lands with the app.
- Capture uses the V4L2 read() method (one frame per request);
  streaming mmap/QBUF arrives with the viewfinder.

## What this unlocks

- Camera app v1 on a working sensor: viewfinder (streaming),
  still capture, in-use indicator, permstored-gated.
- On hardware: same daemon + ioctls against a real sensor driver —
  the virtual gate becomes the hardware bring-up checklist.
