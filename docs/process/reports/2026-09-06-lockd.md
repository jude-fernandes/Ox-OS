## Scope

Phase 3 chunk 11: the lock security architecture, completed.

### 1. `ox-lockd` — the lock-secret owner

A supervised daemon owns `/data/ox/lock.pin` (v1 salted iterated
SHA-256 records — 16-byte urandom salt, 4096 rounds, via ox-pay-proto's
RFC-tested SHA-256). Exactly one writer; the store leaves the UI layer
entirely:

- `verify {pin}` → `{ok}` — ox-shell delegates unlock here and FAILS
  CLOSED (unreachable daemon or malformed reply = no unlock).
- `enroll {current,new}` → rotation with policy enforced at the
  daemon: current must verify, new must be 4–8 digits, the store write
  is atomic (temp + rename), and lockd **self-verifies** the rotation
  before acknowledging — it journals
  `pin-changed old-rejected=true new-accepted=true` only after
  confirming the old secret no longer passes and the new one does.
- Denial telemetry (counted, sampled journal) for future
  lockout/throttle policy.

The shell's secret-handling code was DELETED — the hash, the store
format, and the DEV enrollment now live only in lockd. The lock screen
is replaceable UI; the secret is not in it.

### 2. Settings — user-chosen PIN enrollment

A pad-based three-stage Change PIN flow (current → new → confirm) in
ox-settings: mismatch bounces to the new-PIN stage with an error strip
(no daemon call), wrong current PIN is refused by lockd, and the
digits exist in plaintext only in the two processes' RAM — never on
disk, never over the serial console.

### 3. The compositor got its final architecture: the present thread

The gate's first runs re-awakened the flip wedge: flip PACING limits
queued flips, but the blocking SETCRTC still executed under the
display mutex — one slow host drain (120+ s, kernel hung-task trace
again) froze every repaint and input handler behind it. The fix is the
real compositor split:

- **Renderers** (IPC requests, pointer moves) never touch the DRM fd.
  They clone the (small, now-`Clone`) scene and post *snapshot +
  damage* to a latest-wins queue (`DisplayPipe`). Pure memory work.
- **One present thread** exclusively owns the `DrmOutput`: it waits
  for damage, renders the snapshot into the framebuffer, and performs
  the paced flip. If the host takes minutes to drain the vring, ONLY
  the present thread waits — input routing, IPC, and window
  management continue; newer damage overwrites pending damage
  (latest-pixels-wins).

This matches how real compositors isolate presentation from
composition; the virtual target's pathologies forced the discipline
early — which is the virtual-first strategy working as intended.

## Gate

`tools/pin-gate.sh`: boot (shell + lockd + intentd supervised) →
resourced drill settles → PIN unlock 1234 (through lockd's verify —
the fail-closed wiring proven live) → Settings → Change PIN →
**wrong-current leg**: 9999/5678/5678 → `pin-enroll-refused` →
**rotation leg**: 1234 → 5678 → 5678 → `pin-changed old-rejected=true
new-accepted=true` + `settings-pin-changed` → screendump. The drill is
13+ taps across 4 pad interactions — the longest input sequence any
gate has run — and completed without a single lost event on the
present-thread compositor. Artifact: `2026-09-06-lockd.png`.

## Honest limits

- The gate verifies the rotation through lockd's self-check; a
  full relock-and-unlock-with-new-PIN cycle needs a shell re-lock
  feature (lock button) — next UX chunk.
- No attempt throttling yet (denial counter journaled, policy TBD).
- Duress PIN / panic wipe build on lockd's enroll op but are Phase-5.
- The present thread's render is snapshot-based: a burst of updates
  can skip intermediate frames by design (that is what latest-wins
  means); damage tracking keeps the cost bounded.
