# Bluetooth bring-up — chunk 33, Phase 4, 2026-09-09

## Claim

Ox OS runs the REAL Bluetooth stack end to end on the virtual target:
kernel Bluetooth core + hci_vhci giving two virtual controllers on
/dev/vhci, both powered up through the kernel's own HCI init, one
controller ADVERTISING "Ox-Phone" (flags + complete local name over
raw LE commands) and the other's LE scan RECEIVING the advert across
the shared virtual air (23 reports, real LE advertising-report events
delivered through a real HCI socket). Nothing is mocked: the BT stack
is the kernel's own and the tools are BlueZ's; only the radio is
emulated — by Ox's own radio server, not an emulator binary. On
devices the same stack talks to real chipsets through the same HCI
transport.

## Stack layers (all gated)

1. **Kernel** (fragment in `kernel/kernel.nix`): BT + BT_HCIVHCI as
   modules (hci_vhci exposes /dev/vhci); AF_ALG user-crypto
   (CRYPTO_USER_API_SKCIPHER + CRYPTO_CMAC) built in — btvirt's
   crypto setup needs ecb/cmac aes. The module set ships
   xz-decompressed into the rootfs (`bt-modules` derivation), same
   shape as the Wi-Fi chunk.
2. **Radio server**: ox-btair — Rust, std-only, static aarch64 musl,
   5 unit tests that run in EVERY payload build (workspace-test is
   wired into the payload). One process opens BOTH /dev/vhci fds
   (per-fd vendor handshake: write [0xff, opcode], read 4-byte
   create reply), serves each kernel controller's full H4 command
   stream, and relays LE advertising between the radios through
   shared state + a delivery watcher (continuous re-delivery every
   250 ms, like a real advertiser).
3. **Tools**: bluez cross-built for musl (hcitool, hciconfig, btmgmt)
   with full store closures shipped in the rootfs.
4. **Selftest** (s6 longrun `bt-selftest`): wake lock with
   powerd-socket wait + ack retry → dependency-ordered insmod (rfkill
   crc16 ecc ecdh_generic bluetooth hci_vhci) → wait /dev/vhci →
   **wait for powerd's boot PM selftest to resume** (see finding 3) →
   ox-bt-probe framing check → attach ox-btair (3 respawn passes) →
   power both controllers (EALREADY-tolerant) → name hci0 "Ox-Phone"
   → hci1 advertises over raw LE commands → hci0 scans via
   ox-bt-probe → milestones.
5. **Verification** (`tools/bt-gate.sh` ALL GREEN): `bt-vhci-ok` →
   `bt-controllers-up h1=hci0 h2=hci1` → `bt-named` →
   `bt-discovery-found addr=01:00:00:00:00:02` (scanner saw radio 1's
   fabricated BD_ADDR; "scan: done, 23 advert(s) seen") →
   `bt-stack-ok`. QEMU unlock + keep-awake taps handled by the gate
   (never during the PM suspend window).

## Instructive findings (the cost of doing this honestly)

1. **btvirt is not a radio server you can build an OS on.** The bluez
   emulator lost the /dev/vhci vendor-handshake race (the kernel
   auto-creates a controller 1 s after open; a preempted writer gets
   EBADFD and btvirt exits, killing ALL its radios), and making it
   buildable at all needed `--enable-testing` + a retry patch.
   Replaced wholesale by ox-btair: the OS owns its virtual radio, and
   the gate now exercises code that ships in the payload with unit
   tests, not an emulator binary.
2. **The kernel's controller init is all-or-nothing.** ONE unknown
   command aborts the whole init and the controller never registers.
   The killer was LE Set Event Mask: opcode **0x2001**, not 0x2019 (a
   wrong alias in the first ox-btair). The observed 6.18 init order:
   Reset → version/commands/features/buffer-size/BD_ADDR → event
   masks (0x0c01, 0x2001) → LE buffer/features/states → IAC LAP →
   timeouts → name. Read_Local_Supported_Commands claims only what we
   answer; everything else must still be acked when the kernel sends
   it anyway.
3. **vhci radios are non-persistent across the boot PM selftest.**
   powerd freezes userspace for its one supervised suspend/resume; a
   controller attached across the freeze misses the kernel's 4 s
   command deadline and is gone for good. The selftest waits for
   dmesg `pm-resumed` before touching /dev/vhci and holds a wake lock
   for its lifetime.
4. **hcitool lescan lies through a pipe.** Its per-device output is
   block-buffered when stdout is captured, and `timeout`'s SIGTERM
   throws the buffer away — a scan that SUCCEEDED prints nothing but
   "LE Scan ...". Discovery is asserted by `ox-bt-probe scan`
   instead: raw HCI socket, LE scan enable with duplicate filtering
   off, per-line fflush, clean exit. The first probe version had an
   off-by-one in the frame parse (subevent is buf[3] on a raw HCI
   socket, not buf[4] — the prepended packet-type byte shifts
   everything) and silently discarded every report; the gate caught
   it, and its "other frame" hexdump facility is what makes the next
   mismatch cheap to diagnose.
5. **The kernel holds ADV_IND reports pending for scan-response
   merging.** During active scanning, process_adv_report stores an
   ADV_IND instead of reporting it, waiting for a SCAN_RSP the
   controller must solicit over the air — a one-shot advert on a
   virtual air sits pending forever. ox-btair re-delivers every
   250 ms, which is what real advertisers do anyway.
6. **Nix path-flake source snapshots key on directory mtimes.** Files
   synced into /root/oxbuild with fresh content but old mtimes built
   into stale snapshots three times this chunk. `find -exec touch`
   after every sync, and verify the store snapshot, is now routine.

## What this unlocks

- ox-btd: Bluetooth as an Ox IPC service (bluez mgmt or raw HCI),
  permission-gated scan/pairing, Settings Bluetooth panel — same
  shape as oxwifid.
- LE GATT services + pairing/bonding on the virtual air.
- Audio routing (HFP/A2DP) once a virtual BT audio transport exists.
- On hardware: same kernel stack, real chipset over HCI UART/USB —
  the virtual target's gate becomes the hardware bring-up checklist.
