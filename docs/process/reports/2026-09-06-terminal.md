# ox-term — the Terminal app: keyboard path end to end

Date: 2026-09-06
Status: **DONE — TERM GATE ALL GREEN** (launch → focus → type →
execute → close → reap verified end to end; verdict at bottom)

## Scope

Phase 3 chunk 7: the keyboard input route, exercised by a real app.
ox-term (Terminal) is the first keyboard-driven packaged app: printable
keys accumulate on the prompt line via `key-recv`, Backspace edits,
Enter runs the line through `/bin/sh -c`, output is captured (capped at
20 lines) and appended to a scroll buffer. V1 honestly limits itself to
non-interactive commands, no `cd` state, and the prompt only repaints
on execution (see bug 3 below for why per-keystroke redraws had to go).

Gate (`tools/term-gate.sh`): PIN-unlock → Terminal tile tap →
`shell-intent` → `intent-start` → `term-ready` → CLICK inside the
window (focus must be explicit — creation never steals it) → type
`echo ox-term-gate` + Enter over the QEMU monitor's `sendkey` →
require `term-exec cmd=echo ox-term-gate` → screendump → tap Close →
`term-exit` → intentd reap. F1 delivery probes (an unmapped key, so
oxcom journals arrival independent of focus/apps) are sprinkled
through the boot timeline to bisect injection vs routing vs app.

## Debug journey — the flip flood, and how we found it

This chunk caught the deepest bug yet, plus two app-model bugs.

1. **The compositor flip flood wedged the whole system.** Symptoms
   across runs: keystrokes stopped reaching ANY window after the first
   typing burst, permanently. Bisected with the F1 probes: delivery
   worked at t=47/78/82/146 s and died exactly across the redraw burst.
   The kernel's hung-task detector then named it outright:
   `SETCRTC blocked 120+ s inside virtio_gpu_queue_ctrl_sgs` — the
   Terminal's per-keystroke fullscreen redraws queued fullscreen
   transfers (4 MB each; this driver has no DIRTYFB, so every repaint
   is a full flip) into the virtio-gpu control ring faster than the
   TCG host drained them; the ring filled and the next flip's ioctl
   blocked in D-state while oxcom held the SCENE lock across the
   ioctl — freezing key routing, overflowing the kernel evdev buffer,
   and making QEMU drop all further input. Fix: rendering (pure
   memory writes) and presenting (the vring ioctl) are now separate —
   the scene lock is never held across an ioctl — and flips are paced
   at one per 33 ms, so a burst coalesces host-side onto the latest
   pixels instead of queueing one 4 MB transfer per repaint.
2. **Per-keystroke redraws starved the key queue.** Even with the
   wedge fixed, the app redrew per Backspace (~1 s per commit under
   TCG) while the key hub's bounded queue dropped oldest-first — the
   typed letters were discarded behind a backlog of backspaces.
   Fix: editing no longer redraws; the prompt repaints on execution.
3. **The Close button could never work.** Clicks arrive on
   `click-recv` while the app blocked in `key-recv` — two independent
   blocking queues, and no single-threaded app can service both.
   Fix: a helper connection watches clicks and raises a close flag;
   the main loop wakes on a 1 s key-recv timeout to notice it.
4. **Keyboard reader resilience.** oxcom's per-device evdev reader
   used to exit silently on any read error, permanently killing
   keyboard input. It now journals the error and re-opens the device
   (which also makes USB keyboard hotplug survivable on real
   hardware). Routing is instrumented per key (routed `code/ch →
   win`, `unmapped`, `dropped: no focus`).
5. Injection method note: QMP `input-send-event` with key events
   never delivered usable keystrokes in this setup; the QEMU human
   monitor's `sendkey` (one key per command, ~60 ms pacing — the same
   path the original keyboard-input gate proved) is what the gate
   uses. Environment hazard: a failed run's QEMU outlives the run and
   holds the VNC port — the gate now pkills stale QEMUs before boot.

## Honest limits

- No click/keyboard multiplexing helper exists yet for apps in
  general — each app wires its own second connection (ox-term's
  pattern); the app framework chunk should provide this.
- Prompt editing is invisible until execution (no per-edit repaint).
- Interactive programs, `cd` state, and scrollback gestures remain
  future work; `term-exec` output is capped at 20 lines.
