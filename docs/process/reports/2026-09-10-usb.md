# USB: accessories, quarantine by default — chunk 44, Phase 4, 2026-09-10

## Claim

Plugging a USB device into Ox does NOTHING until the user allows it —
the BadUSB defense, enforced at the kernel's own authorization
switch. A USB storage stick hot-plugged at RUNTIME into a real
(emulated) xHCI bus is enumerated by the kernel, immediately
QUARANTINED by ox-usbd (`authorized=0` — the kernel unbinds its
drivers), and provably exposes NO block device while quarantined.
The device list is served behind permstored `usb.read` (deny
refused, fake = clearly synthetic list with the real stick's
identity asserted not to leak, grant = the real list with
`authorized:false` — the ENFORCED state). The system "allow" tap
(`authorize`) flips the kernel switch, usb-storage rebinds, and the
block device APPEARS. Unplugging is noticed and journaled. The gate
drives the full physical lifecycle with runtime hot-plug/unplug
through the QEMU monitor.

## Stack layers (all gated)

1. **Kernel**: xHCI + usb-storage + sd_mod are BUILT IN (arm64
   defconfig already had them — zero kernel changes this chunk). The
   authorization switch (`/sys/bus/usb/devices/X/authorized`)
   deauthorizes: interfaces deleted, drivers unbound, block device
   removed; authorize=1 re-probes and rebinds.
2. **Daemon** (ox-usbd, new crate): polls /sys/bus/usb/devices every
   500 ms; new devices journal `usb-added` and are immediately
   quarantined (`usb-quarantined`); a startup sweep quarantines
   anything already connected (policy starts at daemon boot);
   removals journal `usb-removed`. IPC: `devices {app}` behind
   `usb.read` (deny/fake/grant, consult journaled); `authorize
   {dev, allow}` is the SYSTEM surface (root oxctl acting for the
   user — the same trust level as the dialog tap), refusing unknown
   devices and journaling `usb-authorized`/`usb-deauthorized`.
   `status` is the permission-free liveness probe. Bus-entry
   filtering (interfaces have `:`, root hubs start with `usb`),
   fake-list shape, and dev-info JSON are unit-tested.
3. **Selftest** (usb-selftest, new): waits for the gate's hot-plug,
   requires the quarantine AND that no /dev/sd* exists while
   unauthorized (`usb-quarantine-no-blockdev` — the negative claim,
   checked in the KERNEL, not the daemon), walks the usb.read matrix
   (deny refused / fake synthetic no-leak / grant with
   authorized:false), then authorizes and requires the block device
   to appear (`usb-authorized-blockdev`).
4. **Gate** (usb-gate.sh): headless; sticks an 8 MiB raw image on
   the cmdline as an idle `-drive if=none`; waits out the PM
   suspend-resume drill; hot-plugs via the HMP monitor
   (`device_add usb-storage,id=stick0,bus=xhci.0,drive=stick`),
   requires the quarantine + matrix + authorize legs, then
   `device_del` and requires `usb-removed`. USB GATE ALL GREEN.

## Instructive findings

1. **Reported state must be the ENFORCED state.** The first gate run
   failed at the grant leg: usbd quarantined the device (kernel-side,
   proven by the missing block device) but its in-memory record kept
   `authorized` as READ BEFORE ENFORCEMENT — true — so the granted
   list lied. The fix is one line (flip the cached flag when the
   enforcement write succeeds) but the class is the whole product:
   a privacy daemon that says `authorized:true` about a quarantined
   stick is as broken as one that doesn't quarantine.
2. **Every gate must wait out the PM suspend-resume drill — daemon
   gates included.** The USB gate hot-plugged at guest t≈11 s and the
   PM selftest froze the machine at t≈15 s; the selftest hung mid
   socket-wait and the gate starved. The app gates learned this in
   chunk 37 (pm-resumed wait + no keep-awake); a NEW gate relearned
   it. Rule: no stimulus before `name=pm-resumed`, whatever layer
   the gate drives.
3. **HMP is enough for runtime device hot-plug.** QMP exists only in
   OX_GFX=1 boots; the always-on HMP monitor socket takes
   `device_add`/`device_del` verbatim — headless gates can drive the
   physical lifecycle without graphics.
4. **s6-rc compiled-DB debugging**: "are my services in the guest?"
   is answerable without booting — unsquashfs the built system.img
   and look at etc/s6-rc/compiled/servicedirs (the compiled dir's
   top level is db/lock/n/resolve.cdb — the servicedirs live one
   level down; grepping the top level wrongly reports them missing).

## Honest scope

- The quarantine race: between kernel enumeration and usbd's poll
  (≤500 ms) a device is briefly bound — a fast driver could touch
  the device once before unbind. True plug-time safety needs kernel
  usbcore `authorized=0` defaults (quotas for a kernel-config
  chunk); this chunk's defense is the daemon sweep + prompt
  quarantine.
- `authorize` is authenticated only by the root socket (no app
  identity, no user-dialog UI yet); the authorization does not
  persist across replug — every plug is a new decision (deliberate:
  fail-safe default).
- No USB-C specifics: CC/role/PD negotiation has no honest virtual
  story on QEMU virt — this chunk is the USB DEVICE-access story
  (storage-class proof); Type-C power/role policy needs hardware.
- No USB HID device exercised (the storage class is the crispest
  negative proof); input-device quarantine follows the same switch.
- No file access yet: authorization proves the block device appears
  (/dev/sd*); mounting untrusted filesystems is a later sandbox
  question.
